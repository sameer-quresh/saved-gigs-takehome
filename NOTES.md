# Notes

## 1. How I worked with AI

We used the **Antigravity** coding assistant to build this take-home project. Our workflow was highly structured and incremental, adhering strictly to the planning mode guidelines:
- **Planning First**: We analyzed the repository structure, read the specification files, and created a complete implementation plan before writing any code.
- **Incremental Approvals**: We broke the task into structured phases and sought developer approval before writing or modifying any files in each phase.
- **Steering and Verifications**: At each phase, we ran type checking (`pnpm typecheck`) and resolved compilation warnings immediately, preventing error accumulation.

## 3. Where the AI got it wrong — and what I did

During Phase 3 compilation checks, TypeScript raised two key type issues where the raw code generated by default was off-convention:
1.  **Union Type Assignability**: The `list` parameter validated by `schema.savedGigs.save.validate(req)` returned a type of `string | undefined`, which could not be directly assigned to the DAO parameter requiring the strict union `"WATCHLIST" | "APPLY_LATER" | "SHORTLIST"`.
    *   *Fix*: Explicitly cast the validated field using `list as SavedList` to satisfy the TypeScript compiler.
2.  **Implicit Any Indexing**: In `saved/page.tsx`, accessing `SavedListLabel[item.list]` raised an implicit `any` error since the database DTO defined `list` as a raw `string`, but `SavedListLabel` expects a key of type `SavedList`.
    *   *Fix*: Added type assertion `SavedListLabel[item.list as SavedList]` to keep the indexing safe.

## 4. Suggestions I rejected

-   **Native PostgreSQL custom ENUMs**: Rejected using native database ENUM structures (e.g. `CREATE TYPE list_type AS ENUM (...)`) because changing values in the future is notoriously difficult in Postgres (requiring complex migrations). Instead, we stuck to `VARCHAR(50)` check constraints.
-   **Prop-drilling in React**: Rejected prop-drilling or React Context for filter state on the saved page, using the requested Zustand store (`useSavedGigsStore`) instead.
-   **Heavyweight ORM**: Rejected using Prisma or TypeORM, sticking to raw SQL migrations and Kysely's query builder to keep performance fast and database mappings transparent.

## 5. Judgment calls, trade-offs, and architecture decisions

### Architecture Decisions
-   **Dual-Registry separation**: Placed TypeBox schemas in `shared/src/schemas` and response interfaces in `shared/src/api`. This prevents compiling validators into the Next.js bundle, shrinking frontend sizes.
-   **Top-level Validation**: Request validation is strictly handled at the controller level. DAOs and Services assume that data passed to them is pre-validated and sanitized.

### Database Design Decisions
-   **Check Constraints**: Enforced allowed enum values (`mode`, `status`, `list`) via SQL `CHECK` constraints on table structures.
-   **Minor Currency Units**: Stored `budget_amount` as integers representing cents (e.g., $150.00 is stored as `15000`) to avoid floating-point rounding issues during calculations.
-   **Indexes**: Added manual indexes to foreign keys (`posted_by`, `gig_id`) and a composite index `(user_id, list)` to optimize paginated reads.

### API Design Decisions
-   **Idempotency & HTTP status codes**:
    *   `POST /api/gigs/:gigId/save` does a database-level `ON CONFLICT (user_id, gig_id) DO UPDATE SET` upsert. It returns `201 Created` for new bookmarks, and `200 OK` if list category or note edits are made (idempotent upsert).
    *   `DELETE /api/gigs/:gigId/save` returns a `204 No Content` success no-op even if no bookmark exists (idempotent delete).
-   **Single-query Pagination counts**: Used PostgreSQL window function `countAll().over().as("total")` to retrieve both paginated rows and the total count in a single query.

### Validation Strategy
-   Enforced strict input validation utilizing TypeBox `strictObject` schemas (which reject unexpected extra fields).

### Authorization Strategy
-   Defined permissions as `'<Action>:<Resource>'` string constants in `shared`. Route guards verify authorization on incoming requests via bearer token lookups.

### Testing Strategy
-   Authored integration tests using Vitest and Supertest. Created a custom Supertest agent to simplify token injections. Truncate `saved_gigs` `beforeEach` test to prevent state pollution.

### Assumptions Made
-   Assumed that attempting to `DELETE` a bookmark for a non-existent gig ID returns `204 No Content` to maintain delete idempotency without leaking database details.
-   Assumed mock auth tokens map sequentially to seeded users (e.g. `user-1-token` -> Alice ID 1, `user-2-token` -> Bob ID 2).

## 6. What I cut, and what I'd do with more time

-   **Optimistic UI Updates**: Due to the time budget, we did not write optimistic rollbacks in UI state during save/unsave actions, relying on loading states and list refetches.
-   **Database query analysis**: We could write database query plans (`EXPLAIN ANALYZE`) to verify index coverage under large datasets.
-   **Custom Collections**: We could let users create custom named lists instead of the fixed three category lists.

## 7. How to run it

### Prerequisites
-   Node.js 20+
-   pnpm 9+
-   PostgreSQL 16+ (or Docker running Postgres)

### Installation
```bash
pnpm install
cp .env.example .env
pnpm --filter shared build
```

### Database Setup
1. Start PostgreSQL via Docker:
   ```bash
   pnpm db:up
   ```
2. Run migrations:
   ```bash
   pnpm db:migrate
   ```
3. Seed mock data:
   ```bash
   pnpm db:seed
   ```

### Running the Apps
Start shared watch-build, backend API, and web Next.js servers concurrently:
```bash
pnpm dev
```
-   **Backend API**: http://localhost:3001
-   **Web UI**: http://localhost:3000

### Running Tests
Execute Vitest integration test suites:
```bash
pnpm test
```
